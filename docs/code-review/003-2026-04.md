## Critical

### CR-003-01 — `game_state` property called as method, silently swallowed

**File:** [controller.py:106](wingman/controller.py#L106)

```python
state = self._analyzer.game_state()   # BUG: game_state is a @property
```

`game_state` is decorated `@property` in [analyzer.py:611](wingman/analyzer.py#L611). Calling it with `()` evaluates the property (returning a `GameState` enum), then calls the enum object as a function — raising `TypeError: 'GameState' object is not callable`. The surrounding `except Exception: state = None` swallows the error, so `state` is always `None` and the maneuver-key mission-cancel logic **never fires**.

**Fix:**
```python
state = self._analyzer.game_state   # remove parentheses
```

## High

### CR-003-04 — Background OCR lock used bare (`with lock:`) from background thread while main loop uses `acquire(timeout=)`

**File:** [analyzer.py:784](wingman/analyzer.py#L784), [analyzer.py:788](wingman/analyzer.py#L788), [analyzer.py:855](wingman/analyzer.py#L855)

The main loop correctly uses `self._background_ocr_lock.acquire(timeout=5.0)` ([analyzer.py:758](wingman/analyzer.py#L758)). The background OCR thread at lines 784, 788, and 855 uses bare `with self._background_ocr_lock:` — no timeout. Per CLAUDE.md: "bare `with lock:` is only safe when both sides run in background threads." Here one side is the main loop. If the background thread is stuck the main loop times out correctly, but if the roles reverse (main loop holds, background blocks) the background thread hangs indefinitely.

In practice the main loop only holds the lock long enough to set a frame reference and start a thread — so it is unlikely to cause a hang. Still a latent risk worth fixing.

**Fix:** Apply `acquire(timeout=N)` or document the hold-time guarantee explicitly.

### CR-003-05 — State flags read and written without a lock

**File:** [analyzer.py:614-622](wingman/analyzer.py#L614), [controller.py:328-330](wingman/controller.py#L328), multiple

`game_state` (property) reads `_game_starting`, `_game_starting_stalled`, `_game_lobby`, `_game_end_b` sequentially with no lock held. These flags are written by the background OCR thread (analyzer.py lines ~818, ~832, ~898) and by controller (lines ~328, ~922-924) concurrently. A reader can see a partially-updated combination (e.g., `_game_lobby=True` and `_game_starting=True` simultaneously) and return a logically impossible state.

CPython's GIL reduces the risk of corruption on individual bool writes, but ordering across multiple flags is not guaranteed.

**Fix:** Introduce a `threading.Lock` (e.g., `_state_lock`) guarding all reads/writes of the four state flags.

## Medium

### CR-003-06 — `FINAL_CONTINUE` OCR check is too broad

**File:** [analyzer.py](wingman/analyzer.py) — `_process_final_continue_region`

The worker checks `if "CONTINUE" in text`. The word "CONTINUE" appears in the game-end "CLICK TO CONTINUE" screen text. If OCR noise bleeds the game-end region into the `FINAL_CONTINUE` crop area, this will false-positive and click a button that may not be visible. `UNLOCK_CLOSE` has a similarly broad "CLOSE" check but the crop position makes overlap less likely.

**Fix:** Require at least two characters of context, e.g. check `"CONTIN" in text and len(text) < 20` to reject long multi-word OCR results, or verify the crop region is sufficiently far from the game-end text zone.

### CR-003-07 — `_run_ocr_in_background` holds no lock between frame-read and null-check

**File:** [analyzer.py:783-790](wingman/analyzer.py#L783)

```python
while True:
    with self._background_ocr_lock:
        full_frame = self._background_ocr_frame      # read under lock ✓

    if full_frame is None:                           # checked WITHOUT lock
        with self._background_ocr_lock:
            self._background_ocr_running = False
        return
```

Between releasing the lock after reading `full_frame` and checking `if full_frame is None`, the main loop could assign a new pending frame. The thread would then exit, leaving `_background_ocr_running = False` and the new frame unprocessed until the next scheduled cycle. Not a crash, but causes missed frames.

**Fix:** Keep the frame reference and the null-check inside the same lock acquisition.

### CR-003-08 — Levenshtein distance implemented twice

### CR-003-09 — `lobby_play_scan_interval` (5 s) vs popup-absence timer (3 s) may never trigger popup check

**File:** [main.py:130](wingman/main.py#L130), [controller.py:311-323](wingman/controller.py#L311)

The popup scan in `start_auto_mission` fires only when the play button has been absent for ≥ 3 consecutive seconds **within a single invocation**. But `start_auto_mission` is called once on lobby entry and then retried every 5 s. Each retry re-captures the frame and re-evaluates. Because `_lobby_play_not_visible_since` persists across retries (not reset per call), the 3-second gate accumulates correctly — but the first retry (at 5 s) will already be past the 3-second threshold, so the popup scan fires on the second entry to the lobby.

No bug, but the comment `"starting 3s popup-check timer"` on the first miss is misleading: the timer doesn't reset per call; it's already ≥ 5 s elapsed before the second check runs.

**Suggested:** Update the log message to clarify that the popup check fires on next retry.

## Low

### CR-003-10 — `analyze_frame` return value inconsistency

**File:** [analyzer.py](wingman/analyzer.py) — `analyze_frame`

`analyze_frame` returns a `dict` with keys `game_state`, `is_respawning`, `respawn_confidence`. Callers in main.py use `.get()` which is safe. But the type is undocumented; a future caller that inspects `game_state` key expecting a `GameState` enum and gets `None` (on a failed frame) has no contract to rely on.

**Fix:** Add a short docstring to `analyze_frame` specifying the returned dict shape and which keys are always present.

### CR-003-11 — No test for `start_auto_mission` popup-click path

**File:** `tests/` — missing

There are no tests covering the new lobby-popup branch added in the current implementation cycle: the 3-second absence timer, popup detection dispatch, REVEAL_ALL double-click, and FINAL_CONTINUE/UNLOCK_CLOSE/TAP_HERE single-click. These paths run in a daemon thread, making regressions silent.

**Suggested tests:**
- `start_auto_mission` when play button absent < 3 s → no popup scan
- `start_auto_mission` when play button absent ≥ 3 s → `scan_region_for_lobby_popups` called
- REVEAL_ALL detected → two `click_crop` calls, ~3 s apart
- No popup detected → no click, no state change

### CR-003-12 — No test for maneuver-key cancel guard (CR-003-01 regression risk)

**File:** `tests/` — missing

The `maneuver_cancel_hotkey` path (which carries the `game_state()` bug from CR-003-01) has no unit test. Once that bug is fixed, a regression test should verify that pressing a maneuver key during `GAME_BATTLE` cancels the mission and that it does *not* cancel during `GAME_LOBBY`.

### CR-003-13 — `_process_tap_here_region` matches "CONTINUE" alone

**File:** [analyzer.py](wingman/analyzer.py) — `_process_tap_here_region`

Checks `if "TAP" in text or "CONTINUE" in text`. The "CONTINUE" branch is identical to `_process_final_continue_region`. If the `FINAL_CONTINUE` crop region is scanned first (it's last in the list), this is moot; but if popup detection order changes, the two functions become ambiguous. Prefer `"TAP" in text or "HERE" in text` to keep the intent distinct.
