## Finding Details

### CR-013-1 — HUD never activates under default config (Critical)

`HudRenderer.from_config()` (hud.py:66) requires both `tracking.enabled` and
`hud.enabled` to be true. The shipped `config.yaml` defaults are
`tracking.enabled: false` / `hud.enabled: true`, so `from_config()` always
returns `None` in a stock checkout — the entire new HUD feature is dead on
arrival. Confirmed by running
`uv run pytest tests/test_target_tracking.py -k from_config -v`:
`test_from_config_enabled` and `test_from_config_tracking_enabled_activates_hud`
both fail with `assert None is not None` against this exact code. The tests
document the intended OR semantics ("tracking.enabled=True must activate
HudRenderer even if hud.enabled=False") that the implementation doesn't match.

**Resolution:** Changed the gate to OR — `from_config()` now returns `None`
only when both `tracking.enabled` and `hud.enabled` are false. All 9
`TestHudRenderer` tests pass, including the two that previously failed.

### CR-013-2 — `eject_and_dive()` has no reentrancy guard (High)

`cancel_mission()` (called at the top of `eject_and_dive()`) only sets a flag;
`is_mission_running()` (`_mission_lock.locked()`) stays `True` until the
mission-runner thread notices the cancel and releases the lock, which can
take longer than `eject_and_dive`'s own 2s `mission_exit_deadline`. Main's
`_handle_no_missiles()` (main.py:552-595, called every 1.5s tick) only guards
on `not ctrl.is_mission_running()`. If background OCR keeps setting
`no_missiles_event` while the mission lock is still held,
`no_missiles_zero_streak` reaches `no_missiles_consecutive_required` (default
2) again and `eject_and_dive()` fires a second time, spawning a second `_run()`
thread that races the first over the same keys. The class already has an
`_ejecting` Event used elsewhere (controller.py:746) to detect an in-progress
eject, but `eject_and_dive()` itself never checks it.

**Resolution:** Added an `if self._ejecting.is_set(): return` guard (with a
debug log) at the top of `eject_and_dive()`, before `cancel_mission()` is
called.

### CR-013-3 — Local-ROI reacquire growth is inert (High)

`use_roi` (tracker.py:115-119) requires `mode == TrackMode.TRACKING`. After a
miss, mode becomes `LOST_GRACE`, so `use_roi` is `False` for the rest of the
grace period — `update()` always falls back to a full acquisition-region scan
regardless of the progressively larger `_roi_rect`/`_current_roi_scale`
computed in `_handle_miss` (tracker.py:182-190). On reacquisition, mode flips
to `TRACKING` and `_current_roi_scale` is immediately reset to the base
`self._roi_scale` (tracker.py:144) before `_roi_rect` is recomputed — discarding
any growth that occurred. `local_roi_reacquire_cycles`,
`local_roi_expand_factor`, and `local_roi_max_scale` currently have no
observable effect on detection.

**Resolution:** `use_roi` now includes `TrackMode.LOST_GRACE` (in addition to
`TRACKING`), so the progressively expanded ROI computed in `_handle_miss` is
actually scanned during the grace period instead of being discarded. The
scale-reset-to-base on reacquisition is unchanged (still correct: once
reacquired, tracking should return to the tightest ROI). All 7
`TestStateMachine` tests still pass unmodified.

### CR-013-4 — Eject afterburner-release gated by unrelated cooldown (Medium)

main.py:986-1005 skips the entire respawn-handling block — including
`ctrl.stop_eject_sequence()` — whenever a new respawn screen appears within
10s of a prior respawn event (`respawn_cooldown_until`, meant for
restart-mission dedup). If a player respawns, quickly runs dry on missiles
again, ejects, and the resulting crash produces a new respawn overlay inside
that 10s window, `stop_eject_sequence()` is never called for it:
`eject_and_dive`'s afterburner-hold loop (controller.py:1044-1049) runs until
the full 120s safety timeout instead of releasing on the actual respawn.

**Resolution:** Hoisted `ctrl.stop_eject_sequence()` out of the
cooldown-gated branch so it fires on every detected respawn, independent of
`respawn_cooldown_until` (the call is idempotent — it only sets an Event).
Confirmed live via `make tp`'s ADR044 replay gate: the log now shows
`RESPAWN DETECTED` immediately followed by `eject_and_dive complete`, rather
than the afterburner hold persisting.

### CR-013-5 — `lobby_stall_since` not reset across lobby re-entry (Medium)

The lobby quick-scan thread's `lobby_stall_since` (analyzer.py:1575) is a
single variable spanning the thread's whole lifetime; it's only reset to 0
when this same thread's own PLAY/READY/CANCEL detection succeeds
(`handled=True`, analyzer.py:1717-1718), not whenever `GAME_LOBBY` is freshly
re-entered. If the lobby is left by some other path while a stall was
partway counted (e.g. the slower main-loop OCR poll mentioned in this
function's own docstring), and `GAME_WAITING` later reverts back to
`GAME_LOBBY`, the stale timestamp can make `elapsed_stall` exceed the 10s
threshold immediately, firing `_on_lobby_stall()` (ESC) the instant the lobby
is re-entered instead of after a genuine stall in the new session.

**Resolution:** The loop now resets `lobby_stall_since = 0.0` on every cycle
where `state != GameState.GAME_LOBBY` (covering `GAME_WAITING` and the
early-`continue` states), so any later re-entry into `GAME_LOBBY` always
starts the stall clock fresh rather than comparing against a stale
timestamp.

### CR-013-6 — `GAME_BATTLE_EJECT` crop keys wrong-case (Low)

`_STATE_CROPS[GameState.GAME_BATTLE_EJECT]` (analyzer.py:470-472) lists
`"health"`/`"ammo_missiles"`, but the real crop-dict keys (used by every
sibling entry and by `config.yaml`) are `"HEALTH"`/`"AMMO_MISSILE"`.
`crops_for_state()` filters by exact name match, so only `"respawn"` survives
for this state. Debug-only impact: the CAPTURE_SCREEN_SHOT hotkey
(controller.py:637) and `show_grid_highlighted` (analyzer.py:1119) both
render without HEALTH/AMMO overlays during eject; the real OCR pipeline
hardcodes the correct keys directly and is unaffected.

**Resolution:** Corrected the two entries to `"HEALTH"`, `"AMMO_MISSILE"`.
Kept the fix minimal (no shared-constant refactor) since no test currently
exercises this table and the surrounding entries follow the same
copy-pasted-literal-set style.

### CR-013-7 — `get_ammo_flares()` lock has no acquire timeout (Low)

The new `get_ammo_flares()` (analyzer.py:822) uses a bare `with
self._ammo_lock:` with no timeout, despite being called every tick from
`main()`'s loop while `_ammo_lock` can be held by the background OCR thread
(analyzer.py:1430-1446). CLAUDE.md requires `acquire(timeout=N)` with a
graceful skip for any lock shared with the main loop. Real-world risk is
currently low (the held sections are brief attribute assignments), but it's a
fresh instance of a pattern the project explicitly prohibits, and it mirrors
the pre-existing (out-of-scope) `get_ammo_missiles()` sibling.

**Resolution:** Both `get_ammo_flares()` and its pre-existing sibling
`get_ammo_missiles()` (same bare-lock pattern, same lock) now use
`acquire(timeout=1.0)` with a guarded release in `finally`, matching the
`ocr_executor` property's existing pattern elsewhere in this file. Fixing the
sibling alongside the flagged method avoids leaving an identical bug
immediately adjacent to the fix.

### CR-013-8 — XKey reconnect loop leaks connections/threads (Low)

The new outer retry loop (controller.py:241-359), added so the keyboard
listener survives XWayland dropping the connection, re-opens `d_rec`/`d_ctrl`
Display connections and spawns a fresh `_stop_watcher` daemon thread on every
reconnect attempt. The `except Exception as e:` handler (controller.py:353-359)
never closes the failed attempt's `d_rec`/`d_ctrl` before looping back or
signals the stale `_stop_watcher` to exit. Repeated transient disconnects
during a long session accumulate leaked X11 connections and parked threads
for the life of the process. Pre-diff code had no retry loop, so this
exposure is new.

**Resolution:** Added a per-iteration `iter_done` Event. The except handler
now sets it and best-effort-closes `d_rec`/`d_ctrl` (each independently
try/except-wrapped, since either may be partially broken). `_stop_watcher`
now waits on `self._stop` in 0.5s increments and exits without acting if
`iter_done` fires first, so a reconnect can no longer leave a watcher thread
holding a stale Display.

### CR-013-9 — HUD acquisition-region rectangle hardcoded (Low)

The HUD's acquisition-region overlay (hud.py:163-166) is drawn with literal
fractions (`0.20`/`0.18`/`0.80`/`0.68`) instead of reading
`tracking.acquisition_region_pct`, duplicating the exact values
`TargetTracker` reads from `config.yaml` (tracker.py:43). Tuning that config
value silently desyncs the HUD's drawn box from the region the tracker
actually scans, defeating the HUD's purpose as a calibration aid.

**Resolution:** `HudRenderer.__init__` now accepts `acquisition_region_pct`
(defaulting to the same literals as before), and `from_config()` reads
`tracking.acquisition_region_pct` from the same config dict `TargetTracker`
uses, passing it through. `_render` draws the box from `self._acq_pct`
instead of hardcoded values.

### CR-013-10 — Blocking HUD write on nearly every tick (Low)

`HudRenderer._render` (hud.py:103-181) does a full-resolution frame copy,
several draw calls, then a synchronous `cv2.imwrite` + `os.replace` disk
write, invoked inline from `main()`'s 1.5s tick loop during battle. Because
`hud.interval_sec` (1.0s) is less than `loop_interval_sec` (1.5s), the
interval gate in `maybe_render` almost never skips a tick — the full
copy/draw/encode/write chain runs on the main thread on effectively every
tick rather than once per second as the interval implies, adding blocking
disk I/O to the real-time control loop's budget for a diagnostic-only
feature.

**Resolution:** `maybe_render()` now dispatches the copy/draw/encode/write
work to a daemon thread (guarded by a non-blocking `_render_lock` so an
in-flight render is skipped rather than queued) and returns the thread handle
(mainly so tests can `join()` it — production callers ignore the return
value). Updated the four `TestHudRenderer` tests that previously asserted on
the output file immediately after a synchronous call to join the returned
thread first; all pass.
