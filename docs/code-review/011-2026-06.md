## Findings

### CR-011-1 — Bare `with _health_lock:` on main-loop path in `eject_and_dive()`

**Severity:** Critical  
**File:** `wingman/controller.py:891`  
**Status:** Resolved

`eject_and_dive()` acquires `self._analyzer._health_lock` with a bare
`with` statement (no timeout). The call chain is:

```
main loop → _handle_no_missiles() → ctrl.eject_and_dive() → with _health_lock:
```

The analyzer's background OCR thread (`_run_ocr_in_background`) also holds
`_health_lock` at multiple points during health/digit scanning. If OCR is
mid-update when missiles hit zero, the main loop blocks indefinitely with no
recovery path.

**CLAUDE.md rule violated:**
> "Any lock that can be held by a background thread must use `acquire(timeout=N)`
> when called from the main loop. Return or skip the cycle gracefully on timeout."

**Required fix:** Replace the bare `with` with an explicit acquire:

```python
if not self._analyzer._health_lock.acquire(timeout=1.0):
    logger.warning("eject_and_dive: _health_lock timeout — skipping health reset")
else:
    try:
        self._analyzer._game_battle_alive = False
        self._analyzer._health_no_digits_since = 0.0
    finally:
        self._analyzer._health_lock.release()
```

### CR-011-2 — GLib callback exception hangs `loop.run()` indefinitely in `portal.py`

**Severity:** High  
**File:** `wingman/portal.py:80`  
**Status:** Resolved

`call("SelectSources", ...)` and `call("Start", ...)` execute inside `on_create`
and `on_select` signal callbacks, which run within `loop.run()`. If `call_sync()`
raises `GLib.GError` (D-Bus timeout at 120 s, permission denied, portal daemon
restart), PyGObject prints the traceback to stderr and swallows the exception.
`loop.quit()` is never called. `loop.run()` blocks forever, hanging Wingman
startup with no error surfaced to the caller.

**Required fix:** Wrap each `call()` inside the callbacks in try/except:

```python
try:
    call("SelectSources", ...)
except Exception as exc:
    state["error"] = f"SelectSources raised: {exc}"
    loop.quit()
    return
```

### CR-011-3 — `_PipeWireBackend.cleanup()` raises `AttributeError` — pipeline never stopped

**Severity:** High  
**File:** `wingman/capture.py:358`  
**Status:** Resolved

```python
def cleanup(self):
    if self._pipeline:
        self._pipeline.set_state(__import__("gi.repository.Gst", fromlist=["Gst"]).Gst.State.NULL)
```

`__import__("gi.repository.Gst", fromlist=["Gst"])` returns the `Gst` module
itself. Accessing `.Gst` on it tries `Gst.Gst` which does not exist →
`AttributeError`. `set_state(NULL)` is never called; the PipeWire pipeline stays
`PLAYING` on every Wingman exit on Linux/Wayland.

Note: this method is also unreachable (see CR-011-7).

**Required fix:** Drop the extra `.Gst`:

```python
self._pipeline.set_state(
    __import__("gi.repository.Gst", fromlist=["Gst"]).State.NULL
)
```

Or cache `Gst` during `_setup()` and use it here.

### CR-011-4 — 10-minute watchdog calls Windows-only `shutdown /s /t 0` — silently fails on Linux

**Severity:** High  
**File:** `wingman/main.py:734`  
**Status:** Resolved

```python
subprocess.run(["shutdown", "/s", "/t", "0"], check=False)
```

On Linux, `shutdown /s /t 0` is not valid syntax. The binary exits non-zero
(`Failed to parse time specification: /s`). `check=False` swallows the error.
The PC never powers off; the unattended watchdog is dead code on the Linux path.

The comment in the code explicitly notes this uses Windows-style flags but does
not address Linux.

**Required fix:**

```python
import sys
if sys.platform == "win32":
    subprocess.run(["shutdown", "/s", "/t", "0"], check=False)
else:
    subprocess.run(["shutdown", "-h", "now"], check=False)
```

### CR-011-5 — `_miss_count` reset causes detection to run on every miss frame, warn-once guard fires every frame

**Severity:** Medium  
**File:** `wingman/capture.py:320`  
**Status:** Resolved

```python
if self._game_offset is None or self._miss_count >= self._REDETECT_AFTER:
    self._miss_count = 0                          # always reset before detect
    self._game_offset = self._detect_game_offset(arr)
    if self._game_offset is None:
        self._miss_count += 1                     # always becomes 1
        if self._miss_count == 1:                 # always True after a miss
            logger.warning(...)
            cv2.imwrite("/tmp/wingman_detect_fail.png", ...)
        return None
```

Because `_miss_count` is reset to 0 before every detection call, it can never
accumulate to `_REDETECT_AFTER = 30`. After each miss it is 1, so:

- The `== 1` "warn once" guard fires on **every** failed frame, not just the
  first.
- `cv2.imwrite()` writes a debug PNG to disk on every miss (at 1.5 s per tick,
  this is continuous I/O while the game is not visible).
- `_detect_game_offset()` is called on every tick when the game is absent. Its
  frame-diff fallback path totals 1 second of `time.sleep()` calls (lines 229–230:
  `for gap_ms in (200, 300, 500)`), blocking the main loop and turning a 1.5 s
  tick into ~2.5 s.

**Required fix:** Increment `_miss_count` before resetting, and only reset when
detection succeeds. Or, move detection off the get_frame() hot path into a
background thread.

### CR-011-6 — `start_weapon_loop()` clears `_mission_cancel`, racing with in-flight `cancel_mission()`

**Severity:** Medium  
**File:** `wingman/controller.py:1089`  
**Status:** Resolved

```python
def start_weapon_loop(self, interval=None):
    ...
    self._mission_cancel.clear()   # line 1089
```

`cancel_mission()` sets `_mission_cancel` to stop running mission threads.
If the user presses End (cancel) and then X (weapon loop toggle) in rapid
succession, `start_weapon_loop()` clears the cancel signal before the running
mission thread has polled it. The mission thread's next
`_mission_cancel.wait(timeout=0.05)` returns False and the mission continues
executing past the cancel request.

**Required fix:** Remove the `_mission_cancel.clear()` from `start_weapon_loop()`.
The weapon loop checks `_weapon_loop_stop`, not `_mission_cancel`, so the clear
is not needed for the weapon loop's own operation.

### CR-011-7 — `Capture` class has no `cleanup()` method — `_PipeWireBackend.cleanup()` is never called

**Severity:** Medium  
**File:** `wingman/capture.py:519` (Capture class definition)  
**Status:** Resolved

`main.py`'s finally block calls `ctrl.cleanup()` and `analyzer.cleanup()` but
never `cap.cleanup()` — the method does not exist on `Capture`. Even if
CR-011-3 (AttributeError) is fixed, the GStreamer pipeline will not be stopped
cleanly at shutdown. The PipeWire portal session remains live; on the next
startup the restore token may reference a stale node, producing black frames or
a repeated portal dialog.

**Required fix:** Add `cleanup()` to the `Capture` class and call it from
`main.py`:

```python
# Capture.cleanup()
def cleanup(self):
    if hasattr(self._backend, "cleanup"):
        self._backend.cleanup()

# main.py finally block
cap.cleanup()
```

### CR-011-8 — `_detect_game_offset()` sleeps 1 second synchronously inside `get_frame()` on the main loop

**Severity:** Medium  
**File:** `wingman/capture.py:229`  
**Status:** Resolved

The frame-diff fallback inside `_detect_game_offset()` waits across three
`time.sleep()` calls totalling 1 s:

```python
for gap_ms in (200, 300, 500):
    time.sleep(gap_ms / 1000.0)
```

This function is called directly from `get_frame()`, which is on the main loop.
During the 1 s block: no frames are analyzed, the FSM does not advance, and
incoming-missile OCR results cannot be acted on. Combined with CR-011-5, this
happens on every tick while the game window is absent.

**Required fix:** Run `_detect_game_offset()` in a daemon thread. Cache the
result and let `get_frame()` read it without blocking.

### CR-011-9 — `click_crop()` silently drops clicks when `game_screen_offset` is transiently `None`

**Severity:** Medium  
**File:** `wingman/controller.py:1463`  
**Status:** Resolved

On Linux, `click_crop()` and `click_grid_region()` return silently when
`game_screen_offset` is `None`:

```python
offset = self._capture.game_screen_offset
if offset is None:
    logger.error("click_crop: game window offset not known yet")
    return
```

`game_screen_offset` can be transiently `None` after `_PipeWireBackend.get_frame()`
sets `_game_offset = None` on an out-of-bounds crop (line 349). Since
`click_crop(block=False)` spawns a daemon thread, the thread may execute in the
narrow window between the reset and the next successful re-detection. Critical
clicks (PLAY, click-to-continue) are silently lost; the FSM has already
transitioned but the UI action never fires.

**Required fix:** Add a short retry loop inside `_do_click()` when offset is
None rather than immediately returning.

### CR-011-10 — `_LinuxXTestKeyboard` listener thread blocks in `record_enable_context()` without checking `_stop`

**Severity:** Low  
**File:** `wingman/controller.py:227`  
**Status:** Resolved

The `XKeyListener` daemon thread calls `d_rec.record_enable_context(ctx, handler)`
which blocks until `record_disable_context()` is called externally (by
`unhook_all()`). The `_stop` threading.Event set by `unhook_all()` has no effect
on the blocking call; the thread cannot self-terminate by checking it.

**CLAUDE.md rule:** "Any long-running daemon thread must be stoppable via a
`threading.Event`. Use `event.wait(timeout=interval)` as the loop tick."

In practice the thread IS stoppable via `unhook_all()` → `record_disable_context()`.
The issue is that on abnormal exit (exception before `cleanup()` runs), the thread
cannot be stopped via the event alone, and `_ensure_listener()` can start a second
listener thread if the first is still alive from a prior session object.
