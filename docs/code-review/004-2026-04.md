## High

### CR-004-01 — `scan_region_for_lobby_popups` scans four crops sequentially; each ~3 s on CPU

**File:** [analyzer.py:866-882](wingman/analyzer.py#L866)

```python
popup_crops = ["REVEAL_ALL", "TAP_HERE_TO_CONTINUE", "UNLOCK_CLOSE", "FINAL_CONTINUE"]
for crop_name in popup_crops:
    ...
    detected, _, text = executor.submit(...).result(timeout=30)
```

Each `executor.submit(...).result()` is a synchronous submit-then-wait: the next
crop is not submitted until the previous future resolves. On CPU-only OCR (~3 s/call)
this takes up to **~12 s total** before returning. The caller (`_start_game_starting_loop`
in controller.py) runs on a 5-second interval, so each call to this method blocks
that loop for more than two full ticks.

**Fix:** Submit all futures before waiting on any result, matching the pattern in
`scan_region_for_play_button`:

```python
futures = {
    name: executor.submit(_process_text_region, get_crop(frame, *self.crops[name][:4]),
                          self.crops[name].text or [])
    for name in popup_crops
    if name in self.crops
}
for name, fut in futures.items():
    detected, _, text = fut.result(timeout=30)
    if detected:
        ...
        return name
return None
```

## Medium

### CR-004-02 — `ocr_reader` property hardcodes `gpu=True`, ignoring the config flag

**File:** [analyzer.py:427](wingman/analyzer.py#L427)

```python
@property
def ocr_reader(self):
    if self._ocr_reader is None and easyocr:
        self._ocr_reader = easyocr.Reader(['en'], gpu=True)   # always GPU
```

The `_use_gpu` module-level flag (set from `config.yaml respawn_detection.use_gpu`)
is respected by `_get_thread_ocr_reader()` (the worker path), but not by the
`ocr_reader` property. Any future caller that goes through the property (e.g., a
new sync scan method) will silently attempt GPU initialization even when
`use_gpu: false`.

At present `self.ocr_reader` is not called anywhere in the active code paths — all
live OCR runs through the thread-pool workers — but the discrepancy is a latent trap.

**Fix:** Replace `gpu=True` with `gpu=_use_gpu` in the property body.

### CR-004-03 — `WM_DELETE_WINDOW` handler in calibrate.py creates an anonymous class instance unnecessarily

**File:** [calibrate.py:310](tests/calibrate.py#L310)

```python
root.protocol("WM_DELETE_WINDOW", lambda: (_on_key(type("E", (), {"char": "q"})()),))
```

`type("E", (), {"char": "q"})()` creates a throwaway class just to produce an
object with a `.char` attribute. The outer `(expr,)` wraps the `None` return from
`_on_key` in a single-element tuple that is immediately discarded. Functionally
correct, but impenetrable at a glance.

**Fix:** Replace with a named stub or a `types.SimpleNamespace`:

```python
import types
root.protocol("WM_DELETE_WINDOW",
              lambda: _on_key(types.SimpleNamespace(char="q")))
```

### CR-004-04 — `_move_to_screenshots_root` fails silently if `test_screenshots/` does not exist

**File:** [calibrate.py:140-153](tests/calibrate.py#L140)

`Path.replace(target)` (a rename) raises `FileNotFoundError` if the parent directory
of `target` does not exist. `_SCREENSHOTS_DIR` is assumed to exist, but there is no
guard. In the happy path the directory always exists (images are already there), but
if a user runs `--add-new-crops` on a freshly cloned repo with no `test_screenshots/`
directory, the move step raises after the crop has already been saved to config.

**Fix:** Add `_SCREENSHOTS_DIR.mkdir(parents=True, exist_ok=True)` before the loop
in `--add-new-crops` mode, or catch the error and warn without aborting.

### CR-004-06 — `scan_region_for_lobby_popups` processes `FINAL_CONTINUE` alongside popup crops

**File:** [analyzer.py:866](wingman/analyzer.py#L866)

`FINAL_CONTINUE` is a post-match "Continue" button, not a lobby-blocking popup — it
appears on a different screen than REVEAL_ALL / UNLOCK_CLOSE / TAP_HERE_TO_CONTINUE.
Including it in the lobby popup scan means every lobby popup check also OCRs the
final-continue region, adding ~3 s per call on CPU when no popup is present (the
scan exits on first hit; FINAL_CONTINUE is last in the list but still searched).

This is also the source of the ambiguity flagged in CR-003-06 and CR-003-13:
both FINAL_CONTINUE and TAP_HERE_TO_CONTINUE match "CONTINUE".

**Fix:** Move `FINAL_CONTINUE` to a separate scan call at the appropriate point in
the game-end flow (where `_game_end_b` is True), separate from the lobby popup path.

**Sequencing note:** Implement after ADR 025 (FSM refactor) so the gate condition
reads `analyzer.game_state == GameState.GAME_END_B` rather than
`analyzer._game_end_b` directly.

## New Functionality Assessment

### `--add-new-crops` calibration mode (calibrate.py)

The new mode is well-structured: validates dimensions before prompting, uses the
filename stem as the crop name (clear convention), saves incrementally after each
crop so a quit mid-session preserves progress, and moves the processed screenshot
out of `to_be_added/` to prevent re-calibration. No functional issues beyond
CR-004-04 above.

### Pending-frame queue in `_run_ocr_in_background`

The while-True loop with `_background_ocr_pending_frame` correctly ensures that the
most recent frame is always processed when the thread is busy, rather than being
silently dropped. This is a solid improvement over the previous single-frame handoff.

The CR-003-07 null-check-outside-lock race is still present (line 629), but the new
pending-frame architecture makes it less impactful: even if a frame is missed, the
next pending frame will be picked up immediately.

### `scan_region_for_play_button` (analyzer.py)

Correctly submits PLAY and READY futures in parallel before waiting on results.
Pattern is consistent with the thread pool design.
