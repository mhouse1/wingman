## Critical

### C-1 — `_run_ocr_in_background` leaks `_background_ocr_running=True` when executor is None
**File:** `wingman/analyzer.py` ~line 772–774

When `_run_ocr_in_background` is called but `self.ocr_executor` returns `None`, the method returns immediately without clearing `_background_ocr_running`. The flag was set to `True` in `_detect_respawn_ocr` before the thread was started (line 742), and it is never reset on this path. After this, every subsequent OCR cache expiry tries to `acquire(_background_ocr_lock)` and then sees `_background_ocr_running == True`, so it sets `_background_ocr_pending_frame` instead of starting a new thread — meaning OCR is permanently silenced for that run.

**Fix:**
```python
executor = self.ocr_executor
if executor is None:
    logger.warning("OCR executor not initialized")
    with self._background_ocr_lock:
        self._background_ocr_running = False
    return
```

### H-4b — `on_enter_GAME_LOBBY` / `on_enter_GAME_BATTLE_MANUAL` call `_on_cancel_mission()` while holding `_state_lock` (2 s lock hold)
**File:** `wingman/analyzer.py` ~lines 536–542, 556–559

`_trigger()` holds `_state_lock` for the entire FSM transition including entry callbacks (line 520). Those callbacks call `_on_cancel_mission()` → `cancel_mission()` → `stop_weapon_loop()` → `_weapon_loop_thread.join(timeout=2.0)`. During that join, `_state_lock` is held for up to 2 s. Any concurrent thread that calls `_trigger()` — the keyboard event thread via `maneuver_key_pressed`, the game_starting loop, or main.py — blocks for the full duration. This creates observable stalls, not a deadlock (the weapon loop thread does not acquire `_state_lock`), but a 2-second hole in FSM responsiveness.

**Fix:** Defer callbacks out of the lock scope. The simplest approach is to collect post-transition side effects in `_trigger()` after releasing `_state_lock`, then invoke them:
```python
def _trigger(self, trigger_name):
    with self._state_lock:
        fn = getattr(self, trigger_name, None)
        if fn is None:
            return False
        fn()   # transitions library fires entry/exit hooks here
    # side-effect callbacks run here, outside the lock
```
This requires entry hooks to not call external callbacks directly; instead, `_trigger()` coordinates deferred invocations.

### C-2 — `_click_through_game_end` crashes when `PLAY` crop is not configured
**File:** `wingman/main.py` ~line 48

`_click_through_game_end` accesses `analyzer.crops["PLAY"]` unconditionally. If the user's config does not define the `PLAY` crop, this raises `KeyError` inside a daemon thread. The GAME_END_B state is then never resolved and the bot hangs in that state indefinitely.

**Fix:**
```python
play_crop = analyzer.crops.get("FINAL_CONTINUE") or analyzer.crops.get("PLAY")
if play_crop is None:
    logger.error("_click_through_game_end: neither FINAL_CONTINUE nor PLAY crop configured")
    return
ctrl.click_crop(play_crop, block=True, count=1, region_name="FINAL_CONTINUE/PLAY")
```

### H-1 — `_health_no_digits_since` read and written without `_health_lock`
**File:** `wingman/analyzer.py` ~lines 845, 854–866

`_health_no_digits_since` is written outside `_health_lock` at line 845 (`self._health_no_digits_since = 0.0`) and read/written again at lines 854–866 — all from the background OCR thread. But `on_enter_GAME_BATTLE()` also writes it at line 549 from whatever thread fires the FSM trigger. There is no lock protecting `_health_no_digits_since`, making these accesses a data race: on CPython the GIL makes float assignment atomic, but the compound read-modify-write `(if now_t - self._health_no_digits_since >= 3.0)` is not atomic between `on_enter_GAME_BATTLE` and the OCR thread.

**Fix:** Move `_health_no_digits_since` reads and writes inside `with self._health_lock`.

### H-2 — `_last_mission` read without lock in `disengage_roll_right`
**File:** `wingman/controller.py` ~line 625

`if self._auto_respawn_restart and self._last_mission and not self.is_mission_running():` reads `self._last_mission` bare, while `_set_last_mission` writes it under `_last_mission_lock`. The `_run` closure runs in a daemon thread; a concurrent hotkey press that calls `_set_last_mission` produces a torn read on non-CPython runtimes and is a logical race on CPython.

**Fix:** Wrap the read with `self._last_mission_lock`:
```python
with self._last_mission_lock:
    mission = self._last_mission
if self._auto_respawn_restart and mission and not self.is_mission_running():
    ...
```

### H-3 — `disengage_roll_right` inner loop uses `time.sleep(duration)` — not interruptible
**File:** `wingman/controller.py` ~line 616

`disengage_roll_right` holds `ROLL_RIGHT_KEY` pressed for `duration` seconds via `time.sleep(duration)`. During this period the End key or a respawn cannot abort the roll cleanly — the `_mission_cancel` event is never checked and `_eject_stop` has no effect on this path. The aircraft will keep rolling right for the full 10 s even after manual cancellation.

**Fix:** Replace with an interruptible loop:
```python
step = 0.1
for _ in range(int(duration / step)):
    if self._mission_cancel.is_set() or self._eject_stop.is_set():
        break
    time.sleep(step)
```

### H-4 — `start_j20_mission` hotkey sets FSM state directly, bypassing transition guards
**File:** `wingman/controller.py` ~lines 191–193

When the U key is pressed while not in GAME_BATTLE, the handler does:
```python
with self._analyzer._state_lock:
    self._analyzer.state = GameState.GAME_BATTLE.name
self._analyzer.on_enter_GAME_BATTLE()
```
This bypasses the FSM's `transitions` library entirely, writing `self.state` directly. The `transitions` library may cache internal state in additional attributes (e.g. `_graph`, history). This also skips any on-exit hooks for the current state (e.g. stopping background loops on leaving GAME_STARTING). `on_enter_GAME_BATTLE` is then called while NOT holding `_state_lock`, which is inconsistent with the rest of the codebase where entry hooks run under the lock via the transitions callback chain.

**Fix:** Use `self._analyzer._trigger("manual_reset")` followed by a proper transition sequence, or add a dedicated `force_to_battle` trigger to the FSM transition table.

### H-5 — `reset_cache` modifies `_ocr_cache` dict without `_ocr_cache_lock`
**File:** `wingman/analyzer.py` ~lines 1228–1229

`reset_cache()` writes `self._ocr_cache['timestamp']` and `self._ocr_cache['result']` without holding `_ocr_cache_lock`. The background OCR thread reads and writes the same dict under that lock. A concurrent call from a test runner or external code creates a data race.

**Fix:** Wrap all three cache resets in their respective locks:
```python
def reset_cache(self):
    with self._ocr_cache_lock:
        self._ocr_cache['timestamp'] = 0.0
        self._ocr_cache['result'] = (False, 0.0, None)
    with self._incoming_cache_lock:
        self._incoming_cache['timestamp'] = 0.0
        self._incoming_cache['result'] = (False, 0.0, None)
    with self._click_to_cache_lock:
        self._click_to_cache['timestamp'] = 0.0
        self._click_to_cache['result'] = (False, 0.0, None)
```

### H-6 — `_click_ready_after_invite` calls `cap.get_frame()` from a daemon thread
**File:** `wingman/main.py` ~line 152

`_click_ready_after_invite` is started as a daemon thread but calls `cap.get_frame()`, which uses `self.sct` — an `mss` instance created on the main thread. The `capture.py` docstring explicitly warns that `mss` uses thread-local storage and calls from other threads "will silently use the wrong context." This can return a corrupted or blank frame and potentially crash `mss`.

**Fix:** Create a new `mss()` context inside the daemon thread (mirroring the pattern used in `click_grid_region` and `capture_screenshot`):
```python
def _click_ready_after_invite():
    time.sleep(1.5)
    with mss() as sct:
        s = sct.grab(cap.get_monitor_rect())
        new_frame = np.array(s)[:, :, :3]
    ...
```

`_process_incoming_region` always returns a 5-tuple `(bool, float, str|None, str|None, list)`. The call site at line 810 unpacks exactly five values:

```python
incoming_detected, incoming_ocr_time, variant_name, incoming_text, incoming_raw = incoming_future.result(timeout=120)
```

**Fix:** Update the docstring to document all five return values, including `raw_texts`.

### M-2 — `_start_game_starting_loop` inner polling loop uses `time.sleep(0.1)` — CLAUDE.md violation
**File:** `wingman/controller.py` ~lines 1085–1101

The `_loop` function inside `_start_game_starting_loop` uses `for _ in range(50): ... time.sleep(0.1)` (lines 1085, 1101) and `for _ in range(good_luck_wait * 10): ... time.sleep(0.1)` (line 1118). These are long-running daemon thread bodies. CLAUDE.md requires `event.wait(timeout=interval)` in daemon thread loops, not bare `time.sleep()`. The `good_luck_event` is the natural wait target here.

**Fix:** Replace the inner 5-second and 13-second polling loops with `good_luck_event.wait(timeout=0.1)` style or similar event-driven waits so `cleanup()` can terminate them cleanly.

### M-3 — `_padlock_loop` and `_weapon_loop` in `start_search_and_destroy_loop` use `time.sleep(0.1)` — CLAUDE.md violation
**File:** `wingman/controller.py` ~lines 544–547, 573–575

Both loops use `time.sleep(0.1)` inside the inner `for _ in range(N)` spin. The `_sdl_stop` event is already available. CLAUDE.md mandates `event.wait(timeout=)` for daemon thread loops.

```python
while not stop.wait(timeout=6.0) and not self._mission_cancel.is_set():
```

### M-4 — Mission-wait loops in `mission_loiter` / `mission_j20` spin at `time.sleep(0.05)`
**File:** `wingman/controller.py` ~lines 785–790, 859–864

Both mission entry points contain:
```python
while not self._mission_complete.is_set():
    if self._exit_event and self._exit_event.is_set():
        ...
    time.sleep(0.05)
```
`_mission_complete` is a `threading.Event`; using `time.sleep(0.05)` instead of `_mission_complete.wait(timeout=0.05)` wastes CPU on 20-Hz busy polling. This is also a CLAUDE.md violation (daemon thread spin without `event.wait`), although these run on the hotkey thread, not the main loop.

**Fix:**
```python
while not self._mission_complete.wait(timeout=0.05):
    if self._exit_event and self._exit_event.is_set():
        ...
```

### M-5 — `analyzer.cleanup()` does not stop the background OCR thread
**File:** `wingman/analyzer.py` ~lines 585–595

`cleanup()` sets `_click_to_stop` and `_lobby_quick_scan_stop`, but the background OCR thread started by `_run_ocr_in_background` has no corresponding stop event and is never joined. On shutdown the executor is shut down with `wait=False`, but the coordinator thread may still be blocked in `future.result(timeout=120)` against a dead pool, causing it to hang for up to 120 seconds before dying. There is also no `_background_ocr_stop` Event, so the loop at line 758 (`while True`) cannot be terminated gracefully.

**Fix:** Add a `_background_ocr_stop = threading.Event()` and check it at the top of the `while True` loop in `_run_ocr_in_background`. Set it in `cleanup()` before calling `executor.shutdown()`.

### M-6 — `_interruptible_sleep` uses `time.sleep` — not event-driven
**File:** `wingman/controller.py` ~line 702

`_interruptible_sleep` is used on the mission-runner thread path. It polls `_mission_cancel.is_set()` in a loop with `time.sleep(interval)`. Since `_mission_cancel` is a `threading.Event`, the correct pattern is `_mission_cancel.wait(timeout=interval)` which returns immediately when the event is set, giving ~interval response latency instead of up to `check_interval` (default 1.0 s) latency.

**Fix:**
```python
def _interruptible_sleep(self, seconds: float, check_interval: float = 1.0) -> bool:
    remaining = float(seconds)
    while remaining > 0:
        interval = min(check_interval, remaining)
        if self._mission_cancel.wait(timeout=interval):
            return False
        remaining -= interval
    return True
```

### M-7 — `eject_and_dive` afterburner hold loop uses `time.sleep(0.5)`
**File:** `wingman/controller.py` ~line 504

The afterburner hold-until-respawn loop at lines 496–504 uses `time.sleep(0.5)` while checking `_eject_stop` and `_is_respawning()`. Since `_eject_stop` is a `threading.Event`, `_eject_stop.wait(timeout=0.5)` gives equivalent timing but responds to cancellation immediately instead of waiting up to 0.5 s for the sleep to complete.

```python
if self._eject_stop.wait(timeout=0.5):

```
(This also eliminates the separate `if self._eject_stop.is_set(): return` check at line 498.)

### L-5 — `ocr_executor` property is not thread-safe
**File:** `wingman/analyzer.py` ~lines 497–516

The `ocr_executor` property checks `self._ocr_executor is None` and `self._ocr_executor_initialized` without any lock. Two threads calling `ocr_executor` simultaneously on cold start can both see `_ocr_executor is None` and both create a `ThreadPoolExecutor`, with the second overwriting the first (leaking 13 threads). The pre-warm tasks submitted on the first executor would be abandoned.

**Fix:** Protect the lazy-init block with a lock (reuse `_background_ocr_lock` or add a dedicated `_executor_init_lock`):
```python
with self._background_ocr_lock:
    if self._ocr_executor is None and easyocr and not self._ocr_executor_initialized:
        ...
return self._ocr_executor
```

### L-6 — `_get_thread_ocr_reader` acquires `_ocr_init_lock` even when reader is already initialized
**File:** `wingman/analyzer.py` ~lines 61–71

The check `if not hasattr(_thread_local, 'reader')` is done before acquiring `_ocr_init_lock`. This is correct for the hot path (reader already present → no lock taken). But when `_thread_local.reader` has been set to `None` on a previous failed init (line 63), `hasattr` returns `True`, so the worker will never retry init even if the first attempt failed transiently. The reader stays permanently `None` for that thread.

**Fix:** Change the guard to `if not getattr(_thread_local, 'reader', None):` so a `None` reader is retried on the next call.
