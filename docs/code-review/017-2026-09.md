# Code Review 017 — Static review of the current architecture and lifecycle risks

| Status | Date       | Wingman Version |
|--------|------------|-----------------|
| Draft  | 2026-09-18 | 1.8.9           |

## Scope

Static review of the current working tree without executing Python or the game runtime. This pass reviewed the main runtime and architecture layers, with emphasis on the boundaries between capture, OCR, FSM state transitions, controller injection, lifecycle shutdown, and the behavior-tree decision layer.

## Review summary

The project is substantially stronger than a typical automation prototype. The runtime has a real control-system feel: explicit watchdogs, configuration validation, focus guards, nested-display handling, and a strong incident-driven design history are all present and actively used. The codebase is also clearly built around real-world failure modes rather than a clean demo-only path.

The dominant risk is not a single glaring bug. It is cumulative complexity: the planner, the state machine, the tactical controller, the OS input surface, and the background OCR infrastructure all interact across many threads and timing windows. This is workable, but it needs strong boundary discipline to remain maintainable and safe.

## Actionable items

| ID | Severity | Area | Action item | Rationale |
|----|----------|------|-------------|-----------|
| CR-017-01 | High | Architecture | Split the responsibilities of the controller object into separate layers: input injection, tactical action, mission orchestration, and safety gating. | [wingman/controller.py](../../wingman/controller.py) currently owns too many concerns in one class: mission lifecycle, hotkeys, click dispatch, keypress logic, and tactical behavior. This is the biggest maintainability and regression risk in the codebase. |
| CR-017-02 | High | Lifecycle | Define a single lifecycle contract for every background worker: stop event, cleanup order, and explicit shutdown semantics. | The project already has watchdogs and thread cleanup, but the number of background workers is large and the shutdown paths are spread across multiple modules. A clear contract will reduce deadlocks, stale threads, and silent late input. |
| CR-017-03 | High | State machine | Centralize the transition invariants for analyzer/controller handoff and document their ordering rules. | The system depends on precise ordering between OCR-derived state, controller actions, and FSM transitions. A drift in transition ordering can silently produce stale actions or delayed safety reactions. |
| CR-017-04 | High | Safety | Keep the injection gate and focus-guard policy as a narrow, single-source safety contract. | The code is correct in intent, but the safe path is important enough that it should be isolated from tactical logic and not be implicitly affected by new mission features. |
| CR-017-05 | Medium | OS integration | Keep display, X11, PipeWire, and Wine/Proton assumptions behind explicit adapters rather than letting them bleed into runtime logic. | The project is targeted at a hard environment and the display assumptions are non-trivial. A host-specific branch should remain visible and isolated instead of becoming an implicit dependency of the main loop. |
| CR-017-06 | Medium | Behavior tree | Make the snapshot contract explicit and versioned: which values are frozen per tick, which are live, and which are intentionally stale. | The tree consumes a complex snapshot of analyzer state in [wingman/behavior_tree.py](../../wingman/behavior_tree.py). This is a high-value architecture, but the correctness requires exact semantic boundaries between frozen and live data. |
| CR-017-07 | Medium | Config discipline | Treat configuration schema and runtime config as a strict contract, and avoid any new keys or defaults that are not intentionally added to both. | [wingman/config_schema.py](../../wingman/config_schema.py) is a good safeguard. It should continue to be the enforcement point for any new tuning or behavior change. |
| CR-017-08 | Medium | Observability | Keep watchdogs, logs, and session artifacts as first-class evidence components, not as afterthoughts. | The history in [wingman/main.py](../../wingman/main.py) and the recorded design comments show the project learns from operational incidents. It should keep preserving evidence for every shutdown and stall path. |
| CR-017-09 | Low | Testability | Reduce cross-coupling between high-level mission behavior and low-level test scaffolding. | The repo has a strong testing culture, but some tests are tightly coupled to the runtime environment and can obscure the difference between real logic failures and harness artifacts. |
| CR-017-10 | Low | Documentation | Keep design intent next to the code that enforces it, especially around race conditions and safety decisions. | The project already documents incident-driven fixes well. This should stay a habit so future code does not silently invalidate old safety assumptions. |

## Recommended order of work

1. CR-017-01: split the controller responsibilities before adding more tactical features.
2. CR-017-02: formalize the thread lifecycle contract and shutdown ordering.
3. CR-017-03: document and enforce state transition ordering rules between analyzer, controller, and behavior tree.
4. CR-017-04 and CR-017-05: keep the safety and OS-integration boundaries narrow and explicit.
5. CR-017-06 through CR-017-10: improve maintainability, observability, and configuration discipline as follow-on work.

## Notes

- This review was static only. No Python interpreter, test runner, or game runtime was executed during the pass.
- The project has a clear culture of learning from real failures, which is a major strength. The actionable recommendations above are about preserving that discipline as the codebase grows.
- The strongest signal in the current tree is that the architecture is already capable, but the next phase of work should prioritize clarity of boundaries over feature breadth.
