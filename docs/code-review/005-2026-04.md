## Change 1 — `game_state` priority inversion (`analyzer.py:537`)

### What changed

The health shortcut that returned `GAME_BATTLE` when `_health >= 1` was evaluated **before** the explicit state flags (`_game_lobby`, `_game_waiting`, etc.). Moved it **after** all explicit flags.

### Root cause

After a battle ends and the player returns to the lobby, `_health` still held the last observed value (e.g. 204). This caused `game_state` to return `GAME_BATTLE` even when `_game_lobby = True`, defeating every state-guard that depended on `game_state`. Background OCR (health, ammo, flares, missiles) kept running for the full lobby duration rather than stopping on lobby entry.

### Review

**Correct.** The health shortcut is a performance optimisation — it avoids acquiring the lock when other flags are set. It must not override explicitly-set state. The fix restores the intended priority: explicit flags win, health is a tie-breaker.

**Risk:** Low. The only observable behaviour change is that `game_state` now returns `GAME_LOBBY` (or other explicit states) while `_health` is still positive. All call sites that acted on this were already guarded by the explicit flags; they now get a correct state reading.

**Observation:** `_health` is never reset to `None` when entering GAME_LOBBY. The health shortcut remains active for the next GAME_BATTLE entry, which is the desired behaviour. No additional reset is needed.

## Change 2 — `start_search_and_destroy_loop` liveness check (`controller.py:625`)

### What changed

The "already running" guard checked `_sdl_stop is not None and not _sdl_stop.is_set()`. Added `and self._sdl_padlock_thread.is_alive()` so the guard only blocks when the thread is actually alive.

### Root cause

When the padlock/weapon loops exit because `_mission_cancel` is set (rather than because `_sdl_stop` is set), `_sdl_stop` is never set. On the next call to `start_search_and_destroy_loop`, the guard sees `_sdl_stop not None and not is_set()` → returns "already running", even though both threads are dead. Result: no search-and-destroy activity for the rest of the mission.

### Review

**Correct.** Thread liveness is the authoritative signal here.

**Alternative considered:** Setting `_sdl_stop` inside the loop body's `finally` block when `_mission_cancel` triggered the exit. This would also fix the guard but creates a secondary invariant ("stop event always set when threads exit") that would need to be maintained everywhere. The liveness check is more localised.

**Edge case:** There is a narrow TOCTOU window — thread could exit between `is_alive()` check and `start()` call — but this window only causes a duplicate no-op start, not a missed start. The duplicate thread would exit immediately on its first `_mission_cancel.is_set()` check. Acceptable.

**Observation:** `_sdl_weapon_thread` liveness is not checked, only `_sdl_padlock_thread`. Since both are started together and share the same `_sdl_stop`/`_mission_cancel` signals, they should always exit in the same window. If the weapon thread ever diverges (e.g. an unhandled exception), the guard could still false-positive. Consider also checking `_sdl_weapon_thread.is_alive()` in a future pass.

## Change 3 — `eject_and_dive` cancellation via End key (`controller.py:559, 583, 143`)

### What changed

Added `_eject_stop = threading.Event()` (cleared at entry to `eject_and_dive`, set by the End-key hotkey). The nose-down 10s sleep is replaced with `_eject_stop.wait(timeout=10.0)`. The afterburner hold loop checks `_eject_stop.is_set()` each 0.5s cycle.

### Root cause

`eject_and_dive` runs in a daemon thread with two long sleeps (10s nose-down + up to 120s afterburner). There was no mechanism to interrupt either phase. Pressing End called `cancel_mission()` but the dive thread continued holding afterburner.

### Review

**Correct.** Using `Event.wait(timeout)` is the idiomatic way to make a sleep interruptible; it replaces `time.sleep` and requires no polling shim.

**Concern — key sequencing:** `eject_and_dive` calls `cancel_mission()` before `_eject_stop.clear()`. If the End key fires between those two lines, `_eject_stop` is set by the hotkey, then immediately cleared by `eject_and_dive`. This is safe because the thread hasn't started yet at that point — the `_run()` closure is created after `_eject_stop.clear()`. No race.

**Key release on cancel:** The `return` inside the `try` block correctly triggers the `finally` clause — Python guarantees `finally` runs even on `return`. Both NOSE_DOWN_KEY and AFTERBURNER_KEY are released in all cancellation paths. No issue here.

## Change 4 — Stale-thread PLAY click guard (`controller.py:394`)

### What changed

Inside `start_auto_mission`'s `_run()` thread, added a state re-check (`if self._analyzer._game_starting or self._analyzer._game_waiting: return`) immediately before the "play button absent 5s → force-click PLAY" branch.

### Root cause

`start_auto_mission` spawns a thread that may take several seconds in OCR. In that window, the main loop could independently advance the state to GAME_WAITING or GAME_STARTING (via CANCEL detection or the GAME_LOBBY stall guard). The thread had a guard at entry but not before the force-click, so it could click PLAY into an active matchmaking session — cancelling the match.

### Review

**Correct and minimal.** Re-checking state at the decision point (not at entry) is the right pattern for long-running threads that touch shared state.

**Observation:** The popup-handling branch at line ~363 (`elif now - self._lobby_play_not_visible_since >= 3.0`) also has no re-check. If state advances to GAME_STARTING during the popup OCR scan, `scan_region_for_lobby_popups` will run and potentially click a lobby popup that is no longer relevant. This is low-risk (popup clicks are harmless in most states) but could be tightened with the same pattern:

```python
elif now - self._lobby_play_not_visible_since >= 3.0:
    if self._analyzer._game_starting or self._analyzer._game_waiting:
        return
    popup = self._analyzer.scan_region_for_lobby_popups(frame)
    ...
```
