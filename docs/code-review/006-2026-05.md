## Bugs

### BUG-1 — `game_state` property called as a function in `controller.py`

**File**: `wingman/controller.py` line 132  
**Severity**: High — TypeError at runtime when maneuver key is pressed during GAME_BATTLE

```python
# maneuver_cancel_hotkey closure — first set of hotkey registrations
state = self._analyzer.game_state()   # ← TypeError: 'GameState' object is not callable
```

`game_state` is a `@property` on `GameStateAnalyzer`; the parentheses are wrong.  
The duplicate registration 40 lines later (`maneuver_key_pressed`) correctly accesses `self._analyzer.game_state` without parens.

**Fix**: remove the parentheses.  
**Note**: the entire `maneuver_cancel_hotkey` closure is also superseded by `maneuver_key_pressed` (see BUG-2 below).

---

### BUG-2 — Same maneuver keys registered twice with two different handlers

**File**: `wingman/controller.py` lines ~120–140 and ~174–195  
**Severity**: Medium — both handlers fire on every maneuver key press

`maneuver_cancel_hotkey` is registered with `keyboard.on_press_key` for NOSE_UP, NOSE_DOWN, ROLL_LEFT, ROLL_RIGHT. Then 40 lines later, `maneuver_key_pressed` is registered for the same four keys with more complete logic (`manual_takeover` FSM trigger, `_ejecting` guard, `_game_battle_since` check). Both fire on every key press.

`maneuver_cancel_hotkey` additionally has BUG-1 (crashes on the `game_state()` call). Because it comes first and raises before reaching `cancel_mission`, the second handler still fires — but the log will show an unhandled exception in the keyboard thread.

**Fix**: remove the entire `maneuver_cancel_hotkey` block (lines ~118–145); `maneuver_key_pressed` subsumes it.

### BUG-3 — `os._exit(0)` in backspace hotkey bypasses cleanup

**File**: `wingman/controller.py` line 152  
**Severity**: Medium — `analyzer.cleanup()` never called; executor and stop-events left dangling

```python
def exit_script_hotkey(e):
    logger.info("Controller: Backspace key pressed - exiting script")
    if self._exit_event:
        self._exit_event.set()
    os._exit(0)   # ← skips main() finally block → analyzer.cleanup() never runs
```

`os._exit` terminates the process immediately without unwinding Python's `finally` stack. The `_lobby_quick_scan_stop` and `_click_to_stop` events are never set; the `ThreadPoolExecutor` is never shut down; any in-flight `keyboard.release()` calls in mission threads are skipped.

Setting `self._exit_event` first is correct; the problem is calling `os._exit` immediately after rather than letting the main loop see the event and exit normally.

**Fix**: remove `os._exit(0)`. The `exit_event.set()` line is sufficient; the main loop's `if exit_requested.is_set(): break` will fire within one `loop_interval_sec`.

### BUG-4 — FSM state forced directly in `start_j20_mission` hotkey, bypassing transition callbacks

**File**: `wingman/controller.py` lines 213–216  
**Severity**: Medium — `on_enter_GAME_BATTLE` never fires; health/ammo sub-state not reset

```python
with self._analyzer._state_lock:
    self._analyzer.state = GameState.GAME_BATTLE.name   # ← raw attribute write
```

This bypasses the `transitions` library's trigger path entirely. `on_enter_GAME_BATTLE` (which resets `_health_no_digits_since` and conditionally sets `alive_event`) is never called. The correct approach is `self._analyzer._trigger("manual_reset")` to reach GAME_LOBBY, then let the quick-scan thread click PLAY — or add a dedicated `force_battle` trigger if immediate GAME_BATTLE entry is required.

### BUG-5 — `_background_ocr_lock` released without `if locked()` guard

**File**: `wingman/analyzer.py` line 807  
**Severity**: Low — violates CLAUDE.md lock-release rule; could raise if `release()` is called when not held

```python
finally:
    self._background_ocr_lock.release()   # ← no if locked() guard
```

Per CLAUDE.md: *"Never use bare `lock.release()` in finally blocks. Always guard with `if self._lock.locked()`."*

**Fix**:
```python
finally:
    if self._background_ocr_lock.locked():
        self._background_ocr_lock.release()
```

## CLAUDE.md Rule Violations

### RULE-1 — `start_weapon_loop` daemon thread uses `time.sleep`, not `event.wait`

**File**: `wingman/controller.py` lines 744–767  
**Rule**: *"Any long-running daemon thread must be stoppable via a `threading.Event`. Use `event.wait(timeout=interval)` as the loop tick — not `while True: time.sleep(interval)`."*

```python
def _loop():
    while self._weapon_loop_active:
        self.fire_active_weapon(hold_seconds=0.1, block=True)
        time.sleep(self._weapon_loop_interval)   # ← not interruptible
```

`stop_weapon_loop()` sets `self._weapon_loop_active = False` and calls `join(timeout=1.0)`, but the thread may be mid-sleep for up to `_weapon_loop_interval` seconds (default 0.5 s) before it sees the flag.

The `_sdl_weapon_loop` in `start_search_and_destroy_loop` correctly uses a 0.1 s tick loop; the same pattern should apply here. A stop `threading.Event` should be created per loop invocation and checked via `event.wait(timeout=0.1)`.

## Dead Code

### DEAD-1 — `GameStateAnalyzer.ocr_reader` property is never called

**File**: `wingman/analyzer.py` lines 549–564

The `ocr_reader` property performs lazy EasyOCR initialization — but always attempts GPU first regardless of the `_use_gpu` flag, and always stores the reader in `self._ocr_reader`. All actual OCR runs via thread-local `_get_thread_ocr_reader()` / `ThreadPoolExecutor`. Nothing in the codebase calls `self.ocr_reader` or `analyzer.ocr_reader`. The property is dead code and its GPU-first logic contradicts the config-driven `_use_gpu` flag.

---

### DEAD-2 — Duplicate Levenshtein implementation

**File**: `wingman/analyzer.py`

Two identical implementations exist:
- `_levenshtein_distance_simple(a, b)` — module-level function (line 214), used by `_respawn_text_matches`
- `GameStateAnalyzer._levenshtein_distance(a, b)` — static method (line 454), used by `_is_respawn_text` / `_is_incoming_text`

Both implement the same DP algorithm. One should be removed and the other used throughout.

---

### DEAD-3 — `_is_respawn_text` and `_is_incoming_text` class methods are never called

**File**: `wingman/analyzer.py` lines 479–543

`GameStateAnalyzer._is_respawn_text` and `GameStateAnalyzer._is_incoming_text` are class methods that wrap `GameStateAnalyzer._levenshtein_distance`. Neither is called anywhere in the codebase. Live detection goes through the module-level `_process_respawn_region` / `_process_incoming_region` functions which use `_respawn_text_matches`. These appear to be leftovers from a prior design and should be removed along with `_levenshtein_distance` (DEAD-2).

## Design Issues

### DESIGN-1 — Double `cancel_mission()` on every GAME_LOBBY entry

**Files**: `wingman/analyzer.py` line 600, `wingman/main.py` line 290

`on_enter_GAME_LOBBY` calls `self._on_cancel_mission()` → `ctrl.cancel_mission()`. The main loop's state-transition handler also calls `ctrl.cancel_mission()` unconditionally when `current_game_state == GameState.GAME_LOBBY`. Both fire synchronously on the same main-loop tick.

`cancel_mission()` is idempotent (sets an event, stops the weapon loop), so this causes no incorrect behaviour. However, it produces a redundant log entry and adds noise when tracing GAME_LOBBY entry. The entry hook call in `on_enter_GAME_LOBBY` is the authoritative one; the main-loop call can be removed.

---

### DESIGN-2 — `_click_to_in_background` does not skip `GAME_BATTLE_MANUAL`

**File**: `wingman/analyzer.py` around line 970

The click-to background thread skips `GAME_END_B`, `GAME_LOBBY`, `GAME_STARTING`, and `GAME_WAITING` — but not `GAME_BATTLE_MANUAL`. During manual play the click-to scan still runs every 5 s and can fire `click_to_detected` → `GAME_END_B`. This is probably intentional (end-of-battle detection should still work during manual mode), but `GAME_STARTING_STALLED` is also not skipped, which means a click-to detection during the stall-recovery loop could transition the FSM to `GAME_END_B` unexpectedly. Worth documenting explicitly.

---

### DESIGN-3 — `_start_game_starting_loop` owns a 180 s timeout that duplicates FSM `starting_timeout`

**File**: `wingman/controller.py` line 1110 (`max_wait = 180`)

The loop has its own 180 s wall-clock timeout that fires `starting_timeout` (→ `GAME_STARTING_STALLED`). The FSM has a `starting_timeout` trigger for exactly this purpose. However, the responsibility for firing the trigger lives in `controller.py` rather than the analyzer or main loop. If the controller is replaced or the loop fails to start, the FSM has no independent safety net to exit `GAME_STARTING`. Consider moving the timeout to the main loop as a guard (similar to the `game_end_b_since` 30 s guard).
