# Code Review 019 — Shutdown, standby and takeover paths

| Status | Date       | Wingman Version |
|--------|------------|-----------------|
| Draft  | 2026-09-25 | 1.8.11          |

## Scope

A project-wide pass over [wingman/](../../wingman/), focused on the thread lifecycle in
[wingman/controller.py](../../wingman/controller.py): which writer threads stop, and in what
order, on Backspace (ADR 099 standby), manual takeover (SAF-001) and shutdown. The
[wingman/analyzer.py](../../wingman/analyzer.py) FSM lock was also reviewed, along with the main
loop's wait in [wingman/main.py](../../wingman/main.py).

Code state: HEAD `8e339a8`. The uncommitted ADR 102 work in `analyzer.py` and `config.yaml`
(another session, in progress) is not reviewed here.

The multi-agent `/code-review max` run was attempted twice. Both runs were stopped by a session
usage limit before any finder agent returned. This review was done in the main session instead,
so its coverage is narrower than a full fan-out: the areas it did not reach are listed at the end.

Checked and found clean against the `CLAUDE.md` concurrency rules:

- No `try: lock.release() except RuntimeError` anywhere.
- Every `while True` loop in `controller.py` and `main.py` ticks on `Event.wait(timeout=...)`
  rather than `time.sleep`.
- Analyzer getters that the main loop calls use `acquire(timeout=1.0)`.

## Findings

| ID | Severity | Summary |
|----|----------|---------|
| CR-019-01 | High | A disengage roll that ends after Backspace restarts the mission, which then flies and fires during standby |
| CR-019-02 | Medium | Pursuit fall-through clears `_eject_stop` and starts a dive after takeover or shutdown has already stopped it |
| CR-019-03 | Medium | The manual-takeover cleanup runs inside `_state_lock`, holding the FSM lock for up to about 5 s |
| CR-019-04 | Low | `cleanup()` does not set `_disengage_stop` or join the pursuit, climb, spawn-guard or weapon-loop threads |
| CR-019-05 | Low | The main loop's `incoming_event.wait()` then `clear()` can drop a wake-up |

### CR-019-01 — Disengage restarts the mission into standby

**Where:** `disengage_roll_right._run` ([controller.py:3793-3858](../../wingman/controller.py#L3793-L3858)), `restart_last_mission`, `_mission_exit_requested` ([controller.py:6925](../../wingman/controller.py#L6925)).

**What happens:**

1. The operator presses Backspace during the 10 s disengage roll. This is triggered by the
   boundary / stuck-geometry paths at [tick_handlers.py:1112](../../wingman/tick_handlers.py#L1112) and [tick_handlers.py:2029](../../wingman/tick_handlers.py#L2029).
2. The Backspace handler sets `_operator_stop_event` and `_exit_event`.
3. The roll loop sees `_exit_event` and breaks. Its `finally` releases ROLL_RIGHT.
4. The thread then waits up to 5 s for the cancelled mission to tear down. It then calls
   `restart_last_mission()` whenever `_auto_respawn_restart and last_mission and not
   is_mission_running()`. It never checks `_exit_event`, `_operator_stop_event` or
   `_manual_takeover_active()`.
5. `restart_last_mission()` has no such check either. It starts `mission_j20` (or the
   configured mission) on a new daemon thread.
6. `_mission_exit_requested()` returns **False** in exactly this case. That is by design: once
   `_operator_stop_event` is set, the operator is meant to be able to restart a mission by hand
   in standby. The new mission therefore runs `start_search_and_destroy_loop()` (padlock and
   weapon fire) indefinitely.
7. Meanwhile the main loop has run `cleanup(keep_hotkeys=True)`. That call unhooked every hotkey
   except Backspace, so the operator cannot take over with i/j/k/l. `_execute_key_press` has
   no standby gate, only the GAME_BATTLE_MANUAL one, and the analyzer is no longer ticking.
   Standby is an unbounded wait by design (ADR 124, [main.py:1883](../../wingman/main.py#L1883)).

**Result:** the operator believes they have the aircraft. Instead, wingman keeps padlocking and
firing until a second Backspace closes MetalStorm. This is the failure the 2026-09-11 note in
`cleanup()` describes, reached by a different route.

**Suggested fix:** gate the restart in one place, `restart_last_mission()` and
`_start_default_mission()`. Refuse when `_operator_stop_event` or `_exit_event` is set, or when
`_manual_takeover_active()` is true. The operator's own `u`/`y` hotkeys call the `mission_*`
methods directly, so standby restart-by-hand is unaffected. Add a test that sets
`_operator_stop_event` and asserts that `disengage_roll_right` completes without starting a
mission.

### CR-019-02 — Pursuit fall-through overrides a stop

**Where:** `pursue_and_engage._run` `finally` ([controller.py:3445-3478](../../wingman/controller.py#L3445-L3478)) and `eject_and_dive` ([controller.py:2971](../../wingman/controller.py#L2971)); same clear in `pursue_and_engage` ([controller.py:3288](../../wingman/controller.py#L3288)).

The pursuit loop breaks with `fall_through = True` on ammo exhausted or the maximum duration. Its
`finally` block then runs `release_tracking_holds()` and a tally log line, and only after that
calls `eject_and_dive()`. `eject_and_dive()` unconditionally does `self._eject_stop_reason = ""`
and `self._eject_stop.clear()`.

Suppose `release_for_manual_takeover()` or `cleanup()` sets `_eject_stop` between the break and
the `eject_and_dive()` call. The stop is erased, and a new eject thread holds NOSE_DOWN and
afterburner. Neither `cleanup()` nor the takeover path joins `_pursuing_thread`, so nothing
narrows the window.

On shutdown, the new thread can start after `cleanup()`'s key-release sweep. That is the
stuck-key-after-exit case `cleanup()`'s docstring was written to prevent. In standby the process
stays alive, so the whole dive runs.

The window is short (one log call), but it lines up with ends of pursuit, which are also when
operators tend to intervene. The same pattern exists at the start of `pursue_and_engage()`
itself (`_eject_stop.clear()`), which relies on its callers to be gated.

**Suggested fix:** in the `finally`, skip the hand-off when `_eject_stop.is_set()`. In
`eject_and_dive()` and `pursue_and_engage()`, return early when the operator has stopped, an
exit has been requested, or takeover is active, before clearing the event. More generally,
`_eject_stop` is a level signal shared by three workers and cleared by every start. A per-run
stop event (as the heatdive thread already uses) would remove this whole class of race.

### CR-019-03 — Takeover cleanup runs under the FSM lock

**Where:** `_trigger` ([analyzer.py:1502-1537](../../wingman/analyzer.py#L1502-L1537)), `on_enter_GAME_BATTLE_MANUAL` ([analyzer.py:2008](../../wingman/analyzer.py#L2008)), `release_for_manual_takeover` ([controller.py:6975](../../wingman/controller.py#L6975)).

`_trigger` documents that side effects are deferred until `_state_lock` is released. But the
`transitions` library calls `on_enter_GAME_BATTLE_MANUAL` from inside `fn()`, which runs under
the lock. That hook emits `MANUAL_TAKEOVER` synchronously, so `release_for_manual_takeover`
runs with `_state_lock` held. That function:

- joins the weapon loop (up to 2.0 s, [controller.py:5520](../../wingman/controller.py#L5520));
- runs three loop stops that each join for up to 1.0 s ([controller.py:3602](../../wingman/controller.py#L3602), [3690](../../wingman/controller.py#L3690), [3772](../../wingman/controller.py#L3772));
- releases every injectable key.

For that whole time, every other `trigger_event` caller blocks on a bare `with
self._state_lock:`. That includes the main loop, which the `CLAUDE.md` rule on main-loop lock
acquires forbids. The mission and eject threads also call `trigger_event` (for example
`eject_started` at [controller.py:6362](../../wingman/controller.py#L6362)). If a thread being joined is itself blocked in
`trigger_event`, each join runs to its full timeout. There is no deadlock, because every join is
bounded, but the takeover can stall the tick for about 5 s.

**Suggested fix:** in `_trigger`, add `MANUAL_TAKEOVER` to `post_callbacks` for
`GAME_BATTLE_MANUAL` (next to `CANCEL_MISSION`) and remove the emit from
`on_enter_GAME_BATTLE_MANUAL`. That puts the takeover on the same deferred path the docstring
already promises.

Check first that no caller relies on the keys being released before `trigger_event` returns.
The takeover hotkey at [controller.py:1449](../../wingman/controller.py#L1449) is the one to look at. Deferral still runs before
`_trigger` returns, just outside the lock, so the ordering seen by the caller is unchanged.

### CR-019-04 — `cleanup()` misses several writers

**Where:** [controller.py:7362-7391](../../wingman/controller.py#L7362-L7391).

`release_for_manual_takeover()` gained `_disengage_stop.set()` on 2026-09-09 ("was missing
entirely"), but `cleanup()` did not get the same line. It relies on the roll loop polling
`_exit_event`, which is fine for SIGTERM and Backspace, but not for a `cleanup()` reached any
other way.

`cleanup()` also joins only the eject, boundary-turn and missile-evade threads. The pursuit,
climb, spawn-guard, afterburner-evade and heatdive threads are signalled but not joined. So a
press already in flight in one of them can land after the step-2 release sweep.

**Suggested fix:** set `_disengage_stop` in `cleanup()`, and join the signalled threads with the
same 1.5 s bound before step 2. A shared helper used by both `cleanup()` and
`release_for_manual_takeover()` would keep the two lists from drifting apart again.

### CR-019-05 — Lost wake-up in the main-loop wait

**Where:** [main.py:1661-1672](../../wingman/main.py#L1661-L1672).

`analyzer.incoming_event.wait(timeout=remaining)` is followed by `incoming_event.clear()`.
Suppose the OCR thread sets the event between `wait` returning and `clear` running, for example
because a second detection landed while the first was being handled. That set is lost. Flares
still deploy on the next loop pass, because `deploy_flares_on_new_incoming` compares
timestamps, but the immediate wake the comment promises is missed and up to one loop interval
of latency is added.

**Suggested fix:** clear before acting and act unconditionally: `if
incoming_event.wait(...): incoming_event.clear()`, then call `deploy_flares_on_new_incoming()`.
Because that function keys on the timestamp rather than on the event, the result is idempotent.
