# ADR 035 — Runtime Performance Release Trend Chart

| Status   | Date       | Wingman Version |
|----------|------------|-----------------|
| Accepted | 2026-05-23 | 1.6.8           |

## Context

The project already has two performance data streams:

1. Test performance trends (`tests/test-output/performance-trends.html`) from `tests/performance_tracking.py`.
2. Runtime performance snapshots (`docs/performance/current/run_*.json` and `docs/performance/release/run_*.json`) written by `wingman/performance.py`.

Runtime data is currently visible in JSON files and log summaries, but there is no single trend chart that answers this release question quickly:

- How does each release compare over time?
- How many OCR cycles contributed to each data point?
- How does the latest unpublished current run compare to published release baselines?

Without contribution size on chart points, small-sample points can look as trustworthy as large-sample points.

## Decision

Create a runtime performance trend chart, modeled after `performance-trends.html`, that:

1. Plots release-series points from `docs/performance/release/run_*.json`.
2. Includes an unpublished current aggregate from `docs/performance/current/run_*.json` as a distinct "current" overlay point on top of prior release history.
3. Exposes contribution size per point (cycle count, session count, reaction events) in hover text.
4. Uses a `performance-history.csv`-style aggregate artifact for fast chart generation, while retaining raw run JSON files as canonical history.

Adopt a two-mode generation policy:

1. **Release mode (finalized):** generated by `make wrelease`, uses release data only.
2. **Preview mode (unpublished-aware):** generated by a separate target, uses release data plus aggregate of all current runs.
3. **Unified preview checkpoint:** `make tp` generates both test preview and runtime preview in the same command so both views reflect one development checkpoint.

The chart is for runtime tracker metrics (ADR 031 path), not test timing metrics.

## Data Rules

1. Release mode points:
- Source all files matching `docs/performance/release/run_*.json`.
- Group by `version`.
- Aggregate crop means with weighted average by crop `n`.
- Report `incoming_cycles` as the sum of incoming `n` across grouped runs.
- Report `session_count` as number of run files in that grouped point.
- Keep release history append-only. Do not delete previously published release run files.
- Emit/update `docs/performance/release/runtime-performance-history.csv` for chart input.

2. Preview mode current aggregate:
- Source all files matching `docs/performance/current/run_*.json`.
- Aggregate current runs by `version` using weighted crop means by crop `n`.
- Plot as `version + " (current)"` even if the version matches an existing release point.
- Keep this aggregate visually distinct (color/symbol) so unpublished data is obvious.
- This aggregate is preview-only and must not be persisted as a release baseline.
- Emit/update `docs/performance/current/runtime-performance-preview.csv` for preview chart input.

3. Metrics to chart:
- OCR crop means: incoming, respawn, health, ammo_flares, ammo_missiles.
- Reaction mean latency.
- Contribution metrics: incoming cycle count, reaction event count, session count.

4. Storage model:
- Raw run JSON files remain the source of truth for auditability and future re-aggregation.
- Aggregate CSV artifacts are derived outputs used for faster chart rendering and simpler tooling.
- If aggregate schema changes, regenerate aggregates from raw run files.

5. Required aggregate CSV schema (both release and preview):
- `mode` (`release` or `preview`)
- `version` (for example `1.6.8`)
- `point_label` (for example `1.6.8` or `1.6.8 (current)`)
- `session_count` (integer)
- `incoming_cycles` (integer)
- `reaction_events` (integer)
- `incoming_mean` (float, weighted)
- `respawn_mean` (float, weighted)
- `health_mean` (float, weighted)
- `ammo_flares_mean` (float, weighted)
- `ammo_missiles_mean` (float, weighted)
- `reaction_mean` (float, weighted)
- `source_run_count` (integer)
- `generated_at` (ISO timestamp)

All means must be weighted using sample counts (`n`) from source run files.

From `docs/performance/release/run_20260511_064715.json`:

```json
  },

```

From `docs/performance/current/run_20260523_025439.json`:

```json
{
  "version": "1.6.8",
  "ocr_crops": {
    "incoming": { "n": 860, "mean": 0.4589, "p95": 0.9281 }
  },
  "reaction": { "n": 6, "mean": 0.4791 }
```

These excerpts show why contribution size must be visible: both points are valid, but reliability differs by sample size.

## Output and UX

1. Generate finalized release chart at `docs/performance/runtime-performance-trends.html`.
2. Generate unpublished-aware preview chart at `docs/performance/runtime-performance-trends.preview.html`.
3. Use interactive hover details including:
- version label
- metric value
- incoming cycles
- session count
- reaction events
4. Keep contribution display hover-only to avoid chart clutter from always-visible labels or intensity overlays.
5. Optionally annotate only low-sample warnings for points below a configured cycle threshold.

## Implementation Notes

1. Add a new script dedicated to runtime tracker trend extraction and chart rendering.
2. Keep test trend tooling (`tests/performance_tracking.py`) unchanged.
3. Add Makefile targets for both runtime modes:
- release mode target, called by `make wrelease`
- preview mode target, used before `make wrelease`
4. Wire `make tp` to run runtime preview generation in addition to existing test preview generation.
5. Keep existing `make test-perf-chart` behavior unchanged for test trends.
6. Fail gracefully when plotly/pandas are missing, with CSV fallback.
7. Update `make wrelease` release-file handling to append new run files to `docs/performance/release/` without removing historical files.
8. During `make tp`, emit a non-fatal warning when runtime preview data is below minimum confidence thresholds.
9. Generate runtime chart input from aggregate CSV artifacts by default, with a rebuild path from raw run files.
10. ADR 035 requires Makefile changes to be implemented (new runtime preview/release targets, `make tp` wiring, and append-only release handling).

11. Required Makefile target names:
- `runtime-perf-csv-release` -> build `docs/performance/release/runtime-performance-history.csv`
- `runtime-perf-csv-preview` -> build `docs/performance/current/runtime-performance-preview.csv`
- `runtime-perf-release` -> build finalized runtime release chart
- `runtime-perf-preview` -> build runtime preview chart

12. Required Makefile wiring:
- `make tp` must run `runtime-perf-preview` after existing test preview steps.
- `make wrelease` must run `runtime-perf-release` after release data promotion.

## Workflow Integration

1. During development, run preview mode to compare current aggregate against full release history.
2. During publishing, run `make wrelease` to move current data into release and regenerate finalized charts.
3. Do not rely on `make wrelease` for unpublished comparison because it clears `docs/performance/current/run_*.json` after copying.
4. Preview mode should aggregate all current runs present before publication.
5. Prefer `make tp` as the single preview command to keep test and runtime views temporally correlated.
6. Runtime preview generation from `make tp` should be best-effort: warn and continue if runtime data is missing.
7. If preview indicates unacceptable performance, discard current run files, apply code fixes, and regenerate preview before release promotion.
8. `make tp` warning policy for runtime preview:
- warn if `docs/performance/current/run_*.json` has fewer than 5 sessions
- warn if aggregated `incoming_cycles` is below 1000
- still generate preview artifacts when possible; do not fail `make tp`

Warning message contract (non-fatal):

- `WARNING: runtime preview has thin data (sessions=<N>, incoming_cycles=<C>; recommended >=5 sessions and >=1000 cycles)`

## Rollout Status

At the time of writing this ADR, current `Makefile` behavior is transitional and not yet fully compliant.

- `wrelease` currently removes `docs/performance/release/` before copy.
- ADR 035 requires replacing that with append-only release handling.

## Acceptance Criteria

1. `make runtime-perf-preview` generates:
- `docs/performance/current/runtime-performance-preview.csv`
- `docs/performance/runtime-performance-trends.preview.html`

2. `make tp` generates test preview artifacts and runtime preview artifacts in one command.

3. When runtime preview data is thin, `make tp` prints the warning contract text and exits successfully.

4. `make runtime-perf-release` generates:
- `docs/performance/release/runtime-performance-history.csv`
- `docs/performance/runtime-performance-trends.html`

5. `make wrelease` appends new release run files without deleting prior release history.

6. Preview chart overlays current aggregate point(s) onto release history; finalized release chart uses release aggregates only.

## Compatibility with Existing ADRs

1. ADR 031 remains the source of runtime measurements.
2. ADR 034 two-tier model is unchanged; this ADR improves observability for the runtime tier.

## Consequences

Positive:

1. Release-over-release runtime OCR changes become visible in one place.
2. Unpublished current data can be compared immediately against release history.
3. Contribution size is explicit, improving trust in interpretation.

Tradeoffs:

1. Adds a second chart pipeline to maintain.
2. Requires clear visual distinction to avoid confusing release and current points.
